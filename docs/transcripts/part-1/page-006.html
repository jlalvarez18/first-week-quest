Lean Feature Planning

Create a compact, decision-complete plan. Assume the executor can derive implementation details from the repository.

Before planning

  • Inspect relevant code, tests, docs, and git state without implementing.
  • Ask only about undiscoverable ambiguity that materially changes product behavior, architecture, safety, cost, or authorization. State reversible assumptions.

Scope-fit gate

List independently releasable capabilities. If any can be delivered and verified without all the others, propose ordered milestones and plan only the smallest coherent one. Shared dependencies are not enough to combine them. Combine only when separation creates an unusable or unsafe intermediate state, or the user explicitly approves the larger blast radius. More than eight execution units means split or seek approval.

Plan contract

Write the smallest safe execution plan:

  1. Outcome: user-visible or operational result.
  2. Approach: chosen design, why it wins, and where tradeoff losses land.
  3. Scope: non-goals, compatibility, and preserved behavior.
  4. Change map: components and likely files; paths are guidance unless contractual.
  5. Execution units: ordered, independently testable deliverables with dependencies and evidence.
  6. Verification: focused, regression, manual, and live gates as applicable.
  7. Risk: failure modes, rollback, and unresolved decisions.

Default to 4–8 execution units and roughly 500–900 words per milestone. Expand only when additional detail prevents a concrete safety or correctness failure.

Durable plan artifact

For substantial or multi-session work, read references/plan-lifecycle.md, save the plan under docs/plans/, and name its path in the handoff. Skip the artifact for trivial or single-edit work.

Detail boundary

Include exact schemas, state transitions, API shapes, or invariants only when load-bearing. Omit micro-steps, routine commands, generic test advice, commit choreography, derivable code, and duplicated specifications. If investigation invalidates the requested direction, say so and recommend the better course.

Code documentation contract

Name documentation impact where the milestone changes public interfaces, state transitions, units or limits, side effects, ownership, concurrency, retry/idempotency, compatibility, or non-obvious rationale. During implementation, add or update language-native documentation for those contracts. Comments explain why or constrain behavior; they do not restate obvious names, types, or control flow. Treat stale or contradictory documentation as a defect and check it during milestone review.

Completion gate

Define the milestone's terminal status:

  • Complete: acceptance criteria and every required automated, manual, or live gate are green; no merge blockers remain.
  • Blocked: only an external dependency or new user authorization prevents progress.
  • Remediation required: review or verification found unresolved blockers.

Budgets control cost, not truth. Exhausting time, tokens, reviews, or fix rounds never makes incomplete work complete. Surface remaining evidence and propose the smallest remediation cycle or request needed authority.

Handoff

End the plan by asking through Claude Code's native plan-approval flow when available, or directly in chat otherwise:

Would you like me to implement this plan?

Wait for explicit approval and exit plan mode through Claude Code's normal flow before editing. Before source edits, create or update the durable plan artifact to in-progress. Then implement the approved milestone. Treat paths and ordinary implementation details as guidance; preserve the outcome and load-bearing contracts. Keep selective code documentation current for public contracts and non-obvious invariants; do not comment obvious code. Use tests and review proportional to risk, preserve unrelated edits, and report material plan deviations.

Do not claim completion unless every required gate is green and no merge blockers remain. Update the plan outcome, evidence, implementation commits, deferred work, and truthful status. If a work budget ends with blockers, report REMEDIATION REQUIRED and the smallest next cycle. After fresh verification, ask exactly:

Would you like me to review this milestone for merge readiness?

If the user agrees, inspect intent, acceptance criteria, the merge-base diff, unrelated edits, documentation, plan outcome, and verification evidence; return READY TO MERGE or NOT READY TO MERGE.

# Guided stops — learn, then try

## 1. Outcome

A stop no longer feels like a test of things you should already know. Each stop opens by
**teaching** in Bean's voice, then asks you to **try it** on a small scenario, then **coaches**
you on the attempt. Being wrong means "apply it differently," never "you did not know."
The full wiki page is one tap away, but you never need it to succeed.

## 2. Approach

Copy Duolingo's lesson shape: concept first, exercise second, feedback that points back to
the concept. Concretely, every stop gets three sections in a fixed order:

1. **Learn.** Bean says one line of why this matters. Under it, 3 short fact cards pulled
   from the wiki page. These are the only things the task needs. Below, a quiet link:
   "Read the full page" (the current Peek content, collapsed).
2. **Try it.** A one-line scenario, then the ask, phrased as *doing*, not *recalling*.
   "A customer was charged twice. Write the message you'd post, and where." The answer box
   and the Check / Are you stuck row stay as they are.
3. **Coach.** Claude grades against the fact cards. On a miss it names which card to
   re-read and that card pulses. The hint ladder stays. "How it grades" is removed; the
   cards *are* the rules, shown up front.

**Why this wins:** the material is on screen, so the task is application, not memory. The
fact cards also give the grader a tighter contract than free-text rubrics. Cost: the page
is longer; scenario copy must be rewritten for all 8 stops.

**Tradeoff losses:** stops become easier. That is correct for onboarding. XP values stay.

## 3. Scope

**In:** content model change, all 8 stops rewritten, Lesson layout, grader prompt and
response shape, card pulse, copy on landing/README/rationale.

**Non-goals:** new stops, changing the path, notes sidebar, team board, the morph.
Progress format is unchanged. Fallback grader keeps working (keywords stay).

## 4. Change map

```
data/stops.json           add: why (1 line), facts (3 strings), scenario, task; rewrite prompts
lib/data.ts               Stop type gains the fields; `prompt` becomes `task`
lib/grade.ts              prompt built from facts + scenario; schema adds factIndex (number|null)
app/api/grade/route.ts    passes factIndex through
components/Lesson.tsx     Learn / Try it sections; remove rubric chip; pulse card on miss
app/globals.css           card-pulse keyframe
app/page.tsx, README.md, docs/rationale.md   "guides, not quizzes" copy
```

## 5. Execution units

1. **Content model.** Extend the Stop type and rewrite `stops.json` for all 8 stops:
   `why`, `facts[3]`, `scenario`, `task`, keep `rubric`, `keywords`, `hints`, `reveal`.
   Rewrite each ask as an action ("write the message", "list what you'd do at 2am").
   Evidence: typecheck passes; every stop has exactly 3 facts.
2. **Lesson layout.** Learn section (Bean line, fact cards, "Read the full page"
   disclosure), then Try it (scenario, task, field, action row). Delete the rubric chip and
   its state. Keep `enter` stagger; cards stagger as a list.
   Evidence: screenshot at desktop and mobile widths.
3. **Coach grader.** Prompt receives facts, scenario, task, rubric. System voice: coach,
   not examiner; feedback names what was applied well, then the one thing to change,
   pointing at a fact card by number. Schema: `{pass, feedback, hint, factIndex}`.
   Fallback returns `factIndex: null`. Evidence: curl right/wrong/spam on 2 stops.
4. **Card pulse.** On a miss with `factIndex`, that card gets a 2-beat amber pulse and
   scrolls into view. Reduced motion: static amber ring only.
   Evidence: manual miss shows the pulse.
5. **Copy pass.** Landing card "Learn by doing" → "Learn, then try". README and
   rationale describe the learn-try-coach shape and why "How it grades" was removed.
   Evidence: grep for "rubric" and "How it grades" in UI copy returns nothing.

Units 1 → 2 → 3 → 4 are sequential. 5 can run any time after 2.

## 6. Verification

- Play stops 1, 5, and 7 end to end with the real key. One miss each. Confirm the
  hint names a card, the card pulses, and the pass feedback praises application.
- Fallback path with the key unset still passes/fails sensibly.
- `npm run build` and `npm run lint` green.
- Mobile: fact cards stack, sheet still opens.

## 7. Risk

- **Facts give away the answer.** Intended. The ask is application, so the facts are
  ingredients, not the answer. Stop 4 (ship a PR) and 7 (Beacon) are the check: the task
  asks for an ordered plan, not a fact.
- **Grader points at the wrong card.** Cards are numbered in the prompt; ask for the
  index explicitly; `null` is allowed. UI tolerates null.
- **Rollback:** revert the commit; progress data is untouched.

**Assumption (reversible):** fact cards always show, never collapse. Say so if you want
them collapsible after a pass.
